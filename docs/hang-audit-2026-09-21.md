# Аудит зависаний EasyEDA Copilot

Дата: 2026-09-21. Проверенный checkout: `eaab013`. Изменений рабочего кода нет.

## Вывод

Проблема не ограничена `execute_js`. Есть шесть мест создания `PQueue`, последовательные цепочки SDK/worker, менеджер фоновых операций и UI-ожидания, для которых завершение внешнего вызова является единственным способом продолжить работу. Незавершающийся Promise способен удержать их навсегда.

Транспортные тайм-ауты уже существуют, но означают «клиент перестал ждать», а не «редактор остановил операцию». Добавление `timeout` к каждой очереди само по себе небезопасно: старая операция может продолжить менять документ после запуска следующей. Этот риск уже присутствует в fallback размещения компонентов.

Реалистичная гарантия первой версии исправлений: каждый запрос получает ответ за ограниченное время; состояние выполняемой операции доступно; после неопределённого результата записи новые изменения отклоняются с понятной ошибкой до безопасного восстановления. Гарантия «любой JS и любой нативный вызов можно остановить и немедленно продолжить редактирование» требует изоляции JS и поддержки отмены/восстановления со стороны редактора.

## Область и ограничения проверки

Проверены явные очереди, Promise-цепочки, циклы ожидания, таймеры, отмена, обработчики MCP, сборщики схемы/платы, checkpoints, SDK Node/Python, сетевые и storage-пути web UI. Просмотрены границы вызовов установленного `eda-copilot-backend@0.2.0`, включая его worker pool и HTTP wrapper. Это не аудит внутренней реализации EasyEDA и не полный аудит отдельных репозиториев backend/router.

Основные сценарии проверены локальными fault-injection тестами с подменённым API, без подключения к редактору. Открытый проект не изменялся. Причину предыдущего живого зависания нельзя точно приписать конкретному `create`: без трассировки этапов зависнуть могли также checkpoint или другой нативный await.

## Найденные риски

### 1. P1 — Основная очередь MCP не ограничивает время выполняющегося задания

- `extension/src/mcp-client.ts:63`: `PQueue({ concurrency: 1 })`.
- `:1980`: deadline проверяется только перед запуском `handleMessage`.
- `:2050`: весь обработчик выполняется внутри этой очереди.
- `mcp/src/bridge/index.ts:165`: при тайм-ауте удаляется ожидающий ответ и отклоняется Promise клиента; активная работа в редакторе не отменяется.

Любой зависший native await блокирует следующие команды. Переподключение и `queue.clear()` не останавливают активную задачу. Heartbeat подтверждает живое соединение, но не продвижение очереди. Ограничение длины очереди предотвращает рост памяти, но не восстанавливает выполнение.

Предложение: общий реестр операций редактора, deadline с момента приёма запроса, текущая фаза/API, независимые status/cancel по точному ID. При истечении deadline — запрет дальнейших шагов старой операции; при неизвестном исходе native write — режим `recovery_required`, а не запуск следующей записи.

### 2. P1 — Execute JS может зависнуть на трёх разных этапах

`extension/src/eda/execute-js.ts:54,60,66`:

1. создание checkpoint;
2. выполнение произвольного AsyncFunction;
3. сериализация результата, например `Blob.arrayBuffer()`.

Все три async-сценария воспроизведены на mocks. Кроме того, синхронный `while (true)` блокирует event loop: таймер и команда отмены в том же контексте не выполнятся. Аналогично опасны тяжёлый синхронный пользовательский код и сериализация с пользовательскими getters/toJSON.

Предложение первой очереди: отслеживать все фазы, возвращать ограниченный по времени ответ и явно обозначать незавершённое выполнение; не объявлять его отменённым только по таймеру. Для надёжной принудительной остановки JS — отдельный terminating Worker/иной изолированный контекст и RPC к разрешённому EDA API. Простая передача proxy вместо аргумента `eda` не изолирует код, пока доступен глобальный API.

Остановка Worker прекращает JS, но не отменяет уже переданную редактору запись.

### 3. P1 — Вложенные очереди сборки и native helpers имеют те же пробелы

- `extension/src/eda/assemble.ts:15,104,669`: очередь сборки и локальная очередь размещения с concurrency 5.
- `extension/src/eda/assemble-source.ts:342`: ещё одна очередь seed-размещения с concurrency 5.
- `extension/src/eda/pcb-assemble.ts:5,1067`: очередь сборки платы.

Без ограничений ожидаются получение примитивов, активация wire snapshot, `create`, `done`, изменения source, refresh, save и часть cleanup/rollback. Например, `assemble.ts:670` ждёт активацию snapshot ещё до входа в try/finally. Тайм-аут только внешней MCP-очереди не завершит внутреннюю очередь. Прямые вызовы из UI также должны проходить через защиту.

`waitForBeautifyComponents` (`mcp-client.ts:187`) имеет nominal deadline 20 секунд, но его `getAll` не ограничен: проверка времени происходит лишь после ответа.

Предложение: единый контекст операции для MCP и UI, передаваемый во вложенные задачи; deadline на каждый внешний await, включая методы возвращённых примитивов (`done`). Не ставить ту же операцию повторно в собственную последовательную очередь: вложенные этапы используют уже выданное право на изменение документа. Учитывать все запущенные параллельно native calls.

### 4. P1 — Тайм-аут размещения уже допускает поздние дубликаты

`extension/src/eda/place-component.ts:39–59`: `create` обёрнут в 10-секундный `withTimeout`, любой reject превращается в переход к следующей библиотеке. `withTimeout` (`utils.ts:27`) — Promise.race без отмены.

В mock-тесте первый `create` задержался; fallback успешно разместил компонент; затем первый вызов тоже завершился. Получилось два размещения. Это не утверждение, что так всегда ведёт себя EasyEDA, а доказательство отсутствия защиты в нашем коде.

Дополнительно: глобальный Promise `SYS_LIB_UUID` ожидается вне этого тайм-аута. Аналогичный шаблон есть в UI `components/chat/component/place.ts:33`: после трёх секунд ожидания `placeComponentWithMouse` запускается следующая библиотека. Интерактивное ожидание пользователя нельзя трактовать как отсутствие компонента.

Повторные попытки seed/wire placement в `assemble-source.ts` также требуют классификации ошибок.

Предложение: отдельные ошибки «точно не найдено», «точно не выполнено», «исход неизвестен». Автоматический fallback/retry допустим только для подтверждённо безопасных отказов. После тайм-аута записи — не повторять, не запускать следующий write, не делать автоматический rollback поверх ещё активного вызова.

### 5. P1 — Очистка PCB и восстановление могут конфликтовать с поздними записями

`extension/src/eda/pcb-assemble.ts:218–260`: чтение/удаление при очистке ограничено пятью секундами, но при `strict: false` ошибка логируется и работа продолжается. Просроченный native delete не отменяется. Следовательно, завершённость очистки неизвестна, даже если код уже перешёл к следующим этапам.

`extension/src/eda/assemble-source.ts:2093` автоматически восстанавливает последний checkpoint в catch. Сам restore не ограничен; при параллельных или просроченных записях восстановление может пересечься с ними. Сохранён только Boolean успешного checkpoint, не его ID.

`extension/src/eda/checkpointer.ts:33` дополнительно ждёт native source/page и AppDB; `restoreCheckpoint` ждёт DB, проверку страницы, иногда пользовательский диалог, затем запись source.

Предложение: различать обычную ошибку и unknown outcome; rollback только когда завершились все native mutations. Хранить checkpoint ID и identity документа в контексте операции. Ограничить cleanup и restore отдельно; сбой восстановления не должен скрывать исходную ошибку. Нельзя обходить неуспешное создание checkpoint и всё равно начинать изменение.

### 6. P1 — Цикл удаления проводов может повторяться бесконечно даже при отвечающем API

`extension/src/eda/rm-compoment-with-connections.ts:421–485`: `do ... while (!end)` перечитывает провода и пытается удалить очередной участок.

В ветке `:340–344` результат `delete` не проверяется, возвращается `end: false`. Если delete возвращает false и wire snapshot остаётся неизменным, алгоритм снова видит тот же провод. `wire-snap.ts` действительно удаляет элемент из cache только при truthy-результате native delete.

Предложение: проверять результат изменения, fingerprint топологии/оставшихся ID и ограничение числа итераций. Допустить небольшой ограниченный период согласования индекса, но при отсутствии прогресса завершаться с диагностикой. Обычный тайм-аут отдельного API этот случай не исправляет.

### 7. P1 — Менеджер операций не гарантирует завершения wait/cancel и освобождения ресурса

`mcp/src/operations/manager.ts`:

- `wait` (`:142`) ограничивает ожидание done, но затем без deadline вызывает `readProgress` (`:163`). Поэтому `wait_ms` не ограничивает весь запрос.
- `cancel` (`:188`) без ограничения ждёт cancelHandler.
- Runner, игнорирующий AbortSignal, остаётся running и удерживает ресурс; если позже успешно вернётся, выставляется completed несмотря на запрос отмены.
- Apply handler (`:225`) также не имеет локального deadline. Повторные apply во время applying не разделяют один in-flight Promise.

Первые три случая воспроизведены. Предложение: возвращать cancel acknowledgement немедленно; отдельно отражать requested/confirmed/unknown. Progress читать с коротким бюджетом и возвращать cached progress при сбое. Ввести deadline жизненного цикла и единственный in-flight apply. Клиентское завершение по таймеру не должно автоматически снимать lock с ресурса, если native write ещё не завершён.

### 8. P2 — SDK и Python worker имеют неограниченные локальные ожидания

- `mcp/src/lib/index.ts:172–198`: выражения/аргументы готовятся до сетевого тайм-аута; `serialize` строит последовательную Promise-цепочку.
- `:220–240`: encode/Blob/file input могут удержать её до обращения к bridge.
- `:257,313`: drain/close ждут незавершённую работу без собственного shutdown budget.
- `mcp/src/lib/worker.ts:8`: последовательная цепочка JSON-lines requests.
- `mcp/python/easyeda_copilot/__init__.py:194–200`: asyncio.Lock удерживается во время stdin.drain/stdout.readline без outer timeout.

Предложение: отдельно ограничить ожидание очереди, подготовку входных данных, RPC и shutdown. При зависшем Node worker Python должен прервать и reap именно свой процесс, отклонить ожидающие запросы и сообщить unknown outcome для уже отправленных изменений. Перезапуск worker не доказывает остановку кода в редакторе.

### 9. P2 — HTTP polling/SSE и backend-вызовы не имеют общего бюджета

- `extension/web/src/api/index.ts:60`: native HTTP wrapper не передаёт AbortSignal.
- `fetchWithTask` (`:65`) по умолчанию имеет Infinity; `/start` выполняется до старта счётчика, а зависший `/status` не даёт проверить deadline. Повторные 404 также не исчерпывают бюджет по умолчанию.
- `api/fetch-sse/fetch.ts`: нет idle deadline и общего retry budget; `getBytes` умеет вызывать reader.cancel, но это не отменяет уже зависшее получение response через native wrapper. Для поздних ответов нужна проверка поколения/отмены перед callbacks.
- `api/relay.ts:317`: fetch/body stream имеют AbortController, но нет собственного time/idle budget.
- `mcp/src/tools/circuit.ts:81,133,203`: поиск компонентов и extractCircuit ожидаются вне таймера bridge. В установленном backend HTTP wrapper имеет retries, но не собственный общий deadline; ELK layout также ожидается без deadline на границе этого tool.

Предложение: один абсолютный deadline на запрос/операцию, короткий per-request deadline для polling, ограничение retry/404, terminal cancelled/expired состояния, idle timeout для потоков и корректная отмена чтения. Для вычислений, которые нельзя отменить кооперативно, использовать worker/process. Длительный здоровый stream не путать с зависшим: idle и total limits настраивать раздельно.

### 10. P2 — Очередь сохранения чата может остановиться и накапливать задания

`extension/web/src/stores/chat-history-store.ts:57,73,83,192`: зависшие init/hydration/DB operation блокируют сохранение. Очередной вызов сохраняет весь набор сессий; новые сохранения добавляются в очередь без coalescing.

Предложение: одно выполняемое сохранение + dirty flag для последнего состояния, лимит ожидания DB, доступное пользователю состояние «изменения ещё не сохранены». После тайм-аута не запускать конкурирующие записи вслепую: abort transaction, если поддерживается, либо отключить persistence до безопасного переоткрытия. Не терять состояние в памяти.

### 11. P2/P3 — Интерактивные ожидания и нагрузка на event loop

- `extension/web/src/eda/schematic.ts:26`: выбор провода запускает native read каждые 200 мс, прекращая ожидание каждого через 150 мс. Неотвечающие native запросы при этом могут копиться. Нужен single-flight и явная отмена/ошибка, а не повторный запуск поверх pending.
- `useBlockDiagramEditor.ts:236`: файл ожидается по onchange, закрытие диалога без выбора не обрабатывается. Это локальное незавершённое ожидание, не блокировка MCP.
- `checkpointer.ts:76`: ожидание пользовательского подтверждения отдельно от машинного выполнения; нужен статус awaiting_user и отменяемый жизненный цикл, а не автоматическое согласие.
- `free-place-searcher.ts:111`: поиск конечный, но вложенные циклы и обход препятствий могут надолго занять UI. Это не доказанный бесконечный цикл. Нужны input limits/yield и бюджет вычисления; тяжёлую геометрию можно вынести в worker.

## Уже имеющаяся защита

- Bridge: лимиты pending requests, тайм-ауты ответов, heartbeat/reconnect. Execute JS: 60 секунд ожидания ответа; сборка обычно 300 секунд. Это не тайм-аут выполнения редактора.
- MCP extension queue: максимум 32 ожидающих запроса и проверка устаревшего deadline перед стартом.
- SDK: после transport failure сессия помечается broken; ошибка уже предупреждает, что выполнение может продолжаться и нельзя автоматически повторять.
- PCB preview: ограниченные по времени шаги; это также не native cancellation.
- Установленный backend PCB layout: process worker pool с task timeout по умолчанию 30 минут и ограничением очереди.
- Routing: объединённые сигнал пользователя и AbortSignal.timeout на один час; нужно сохранять эту защиту и покрыть остальные фазы lifecycle.

Поэтому предложение не состоит в замене всех тайм-аутов одним значением. Нужно согласовать существующие бюджеты и убрать неограниченные промежутки между ними.

## План изменений

### Коммит 1 — Контекст выполнения и наблюдаемость

Общий request/operation ID, deadline, document/instance identity, checkpoint ID, phase, lastProgressAt, текущие native calls, cancellation state. Status/cancel конкретного ID идут вне очереди изменения документа и читают память, не ожидают native API. Бюджет включает время в очереди; queued expired/cancelled задания никогда не начинают работу. На disconnect явно завершать ожидающие клиентские задания, не путать это с отменой текущего native call.

### Коммит 2 — Безопасное прекращение ожидания и защита изменения документа

Типизированные ошибки timeout/cancel/unknown outcome. После отмены контекст запрещает новые шаги, в том числе поздние continuations. По тайм-ауту клиент получает ответ, но право на изменение не выдаётся следующей операции, пока прежние записи не завершились. Если исход неизвестен — recovery_required с быстрым отказом новых mutations и рабочей диагностикой. Начать с консервативной блокировки editor instance там, где нельзя надёжно привязать API к документу.

Встроенные обработчики и UI используют общий механизм; возвращённые primitive.done тоже покрываются. Произвольный execute_js остаётся явно unsafe до изоляции. Не рассчитывать, что только proxy-обёртка или Promise.race остановят такой скрипт.

### Коммит 3 — Устранение локальных причин и неправильных повторов

Запрет fallback/retry после unknown write outcome; лимит/проверка прогресса удаления проводов; ограничение native awaits сборки, checkpoints и rollback; fix bounded wait/cancel/progress/apply. Защита должна охватывать nested queues, а не только их внешний вызов.

### Коммит 4 — SDK, сеть, storage и регрессии

Бюджеты Node/Python RPC/shutdown, HTTP/SSE/polling, coalescing сохранений, single-flight polling UI. Тесты с never-resolving promises, поздним успехом/ошибкой и истекающим deadline в очереди. Этот этап можно разделить на независимые коммиты.

### Отдельный этап — Hard cancellation произвольного JS

Изолированный JS worker + capability RPC к EDA; terminate при deadline/отмене; отслеживание уже отправленных native mutations на стороне редактора. Проверить совместимость с примитивами/методами, Blob, checkpoint scopes, SDK batching и событиями. Это архитектурная работа, не маленькая правка очереди.

## Что разумно включить в первый день

Узкий пакет стабилизации: диагностика текущего задания, быстрый timeout/unknown outcome ответ, запрет новых изменений при неопределённом состоянии, исправление опасных retries и бесконечного удаления проводов, bounded wait/cancel и основные регрессии. Полное покрытие всех UI/storage/SDK путей и hard cancellation обещать за день без реализации и проверки нельзя.

## Выполненные диагностические тесты

Исходные TS-модули собирались esbuild в памяти (`write: false`), выполнялись в Node с mock API; открытый EasyEDA не использовался. Deferred promises после проверки разрешались, тестовые процессы завершились успешно.

1. Незавершённый native await внутри executeJavaScript удерживает slot настоящего PQueue; следующее задание не стартует.
2. Незавершённый checkpoint не допускает запуска JS и удерживает вызов.
3. Незавершённый Blob.arrayBuffer удерживает вызов после завершения JS.
4. OperationManager.wait(id, 1) не завершается за 30 мс из-за pending progress reader.
5. OperationManager.cancel не завершается из-за pending cancelHandler; ресурс остаётся занятым.
6. Runner, проигнорировавший AbortSignal, позднее становится completed.
7. В placeComponent таймер 10 секунд ускорен до 10 мс только внутри тестового процесса: после fallback позднее завершается первый create, счётчик размещений становится равен двум.

Это воспроизведение логики отказов, не end-to-end проверка исправлений: исправления ещё не внесены.

## Критерии приёмки исправлений

- Любой внешний await может быть подменён never-resolving Promise: клиент и status/cancel должны отвечать в заданном бюджете.
- Истёкшая в очереди задача не вызывает API.
- Поздний результат старой задачи не запускает следующий её шаг, не меняет статус нового задания и не вызывает fallback/rollback поверх active write.
- Если native mutation не завершена, новые изменения быстро отклоняются, а не ждут её бесконечно.
- Отмена адресована конкретному ID и не затрагивает следующее задание.
- Проверяются все concurrency slots размещения, direct UI entrypoints и вложенные очереди.
- Зависшие progress reader/cancel handler/storage/SDK worker не блокируют диагностику и shutdown.
- Для hard cancellation отдельно проверяются `await never`, бесконечный синхронный цикл и уже отправленная native запись. Эти случаи имеют разные гарантии восстановления.
